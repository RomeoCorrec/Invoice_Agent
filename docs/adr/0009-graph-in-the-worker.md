# ADR-0009: Running the agent graph inside the worker

- Status: accepted
- Date: 2026-10-26

## Context

ADR-0005 built a job worker with two job kinds, `ingest` and `validate`. ADR-0007 decided the
agent is a fixed LangGraph graph. This step joins them: how the graph is started, how its
state and the business data relate, what happens when the process dies half-way, and how a
human decision reaches a paused run. The first pull request of the graph covers
`ingest -> validate -> request_approval -> apply_decision`; the entry proposal, the posting and
the explanation come next.

## Decision

### One `process` job runs the graph
The `ingest` and `validate` jobs are replaced by a single `process` job whose payload is the
document name. The worker stays the envelope (queue, lease, backoff, trace), and its handler
calls `start_run`. The **run id is the job id**, and it is also the checkpoint thread id and
the `run_id` of every audit event the run writes. A retried job therefore continues the same
run from its last checkpoint instead of starting over: after a model outage during extraction,
nothing is half-written and the retry resumes at `ingest`.

The graph nodes `ingest` and `validate` wrap the services of steps 02 to 04
(`ingest_document`, `validate_invoice`). ADR-0007 listed a separate `match_po` node; the
validation service already matches purchase orders, so there is one `validate` node instead of
a node that would do nothing.

### Each node has its own transaction, and can be replayed
Previously a handler ran inside the worker's transaction, so the work and the job's completion
committed together. A graph needs a commit per node (otherwise there is nothing to resume
from), so delivery of a node is now **at least once** and each node must tolerate a replay.
The window is real: a node commits, the process dies, the checkpoint is not written.

- `ingest` looks for a `receive` audit event carrying the run id; if it finds one it returns
  that invoice instead of ingesting again. The lookup runs in its own short transaction, before
  the extraction, so no connection is held open during a model call.
- `validate` finds the invoice already `validated` or `needs_review` and reports the anomaly
  codes recorded in its audit event.
- `apply_decision` finds the invoice already in the target status and does nothing; if the
  invoice is in any other status it raises, so a decision never applies to an invoice that
  changed in the meantime.

Both replays are tested by running the real node, committing, killing the node once, and
running again; removing any of the guards makes a test fail.

### Two stores, one authority
`invoices.status` and the audit log remain the business truth. The LangGraph checkpoint tables
(in the same Postgres, created by `PostgresSaver.setup()`) only let a run resume. A command
that lists what is waiting asks the checkpoint, not the status: an invoice validated before the
graph existed has no run to resume and is not offered. Alembic is told to ignore the
`checkpoint*` tables, otherwise the model/migration comparison and any autogenerated revision
would propose dropping them.

### The human pause
`request_approval` calls `interrupt` with a summary (figures, anomaly codes, status) and no
document text. Everything before `interrupt` only reads, because the node runs again on resume.
The write is in the next node, `apply_decision`, so it cannot run twice by construction.
A decision has a verdict, a required approver and an optional comment; it is validated before
the run is resumed. `resume_run` refuses when no run is waiting: LangGraph silently ignores a
resume on a finished thread, which would hide a double click.

The decision is stored in the checkpoint as well as in the audit log, so bank details are
redacted **when the decision is built**, not at each place that stores it (an automated review
found the comment in clear in the checkpoint; a test now scans the three checkpoint tables).

### A review command, not yet a web page
`python -m invoice_agent.agent pending|approve|reject|seed` goes through the same functions a
web page will use. It prints text that comes from a document (invoice number, supplier name),
so control characters and bidirectional overrides are replaced before printing.

### The graph is synchronous
The worker and SQLAlchemy are synchronous and `PostgresSaver` is the synchronous saver. The MCP
client is asynchronous; the posting node will bridge with `asyncio.run`, which is safe because
a worker thread has no running event loop.

## Alternatives considered

- **Keep the two jobs and start the graph after `validate`.** Less to change, but the graph
  would only hold the approval and the posting, and the replay problem would be hidden rather
  than solved. The point of the project is an agent that owns the whole flow.
- **One job per node.** Reuses the queue for durability, but duplicates what the checkpointer
  provides and loses the single trace of a run.
- **Run the graph from the API process.** Parsing hostile PDFs would then happen in the web
  process; the worker already isolates it.
- **An asynchronous graph with `AsyncPostgresSaver`.** Needed only if nodes become concurrent;
  it would force the repositories to change for no gain today.

## Consequences

- The invoice's whole story is one graph, one trace, one run id in the audit log.
- Nodes are idempotent by construction and by test; new nodes must follow the same rule.
- Resolved: when a job dies (retries exhausted or a permanent error), a hook run in the same
  transaction moves the invoice of its run to `failed`, with the reason and an audit event.
  A final invoice, or a run that never stored one, is left alone, and a failing hook cannot
  keep the job alive (it runs behind a savepoint).
- Open: checkpoints accumulate; pruning finished runs is not done yet.
- Open: the review command is local. Authentication of the approver belongs to the web step;
  today the approver is whatever name the caller passes, recorded as such.
